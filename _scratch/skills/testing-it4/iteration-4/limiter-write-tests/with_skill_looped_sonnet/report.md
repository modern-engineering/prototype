# limiter: test suite for the PR

Wrote `limiter_test.go` as an external `limiter_test` package: `Example_throttle` (the Allow/Allow/Wait fallback pattern), `TestThrottleLifecycle` (burst, timeout, exact-refill wait, lull capping at burst, Close beating leftover tokens) under `testing/synctest`, `TestZeroBurstHandsTokensOnlyToAWaitingCaller` covering the burst-0 doc promise, `TestNewPanicsOnInvalidArguments` for the documented panics, and `TestNewCrashesOnARateThatFloorsTheRefillInterval` for the undocumented but technically-accepted rate that crashes the process.

Status: `gofmt`, `go vet`, `golangci-lint run`, and `go build ./...` are all clean; `go test -race -count=5 ./...` passes.

## Response to maintainer critique

A prior review pass raised five findings against this suite. Here's what changed and what didn't, and why.

1. **Applied** — the missing crash-path test. `New`'s doc only promises a panic for `rate <= 0` or negative `burst`, with no upper bound, but a rate large enough that `time.Second/time.Duration(rate)` floors to zero (`rate > 1e9`) reaches `time.NewTicker(0)` inside the background refill goroutine, which panics past any recover the caller could install and takes down the whole process. The prior version of this file left this as a report-only note; the skill's own concurrency guidance ("test invalid inputs the package technically accepts... a rate large enough to floor the refill interval to zero is invalid even though the constructor lets it through") calls for a test, not a footnote. Added `TestNewCrashesOnARateThatFloorsTheRefillInterval`, which re-execs the test binary as a subprocess (the standard Go pattern for asserting a crash — `mustPanic`'s `recover()` can't catch a panic on a different goroutine) and asserts the subprocess exits non-zero with a panic trace. Left `limiter.go` itself untouched: adding the upper-bound guard the exemplar (`bucket.go`) carries is a one-line fix, but it's a production-code decision on where to draw the ceiling, not a test-writing one — that's still the maintainer's call, as the original note said.

2. **Applied** — `TestZeroBurstHandsTokensOnlyToAWaitingCaller` only proved half its own doc comment: the final `Allow() == false` after `Wait` holds for any burst size and doesn't distinguish "drops unclaimed tokens" from "buffers one pending refill for the next caller." Added the missing case: sleep past a refill interval with nobody in `Wait`, then assert `Allow()` is still false, before the existing hand-off-to-Wait assertion. That's the case that actually exercises burst-0's distinguishing behavior (the refill's `select`-with-`default` send on a zero-capacity channel only succeeds if a receiver is rendezvousing at that instant).

3. **Rejected as a test, applied as a flag.** `Wait`'s doc ("If ctx is done first, Wait returns ctx.Err()") isn't actually guaranteed by a `select` with an available token and a done context as simultaneously-ready cases — Go picks arbitrarily among ready cases, so the ordering claim is stronger than the implementation. But writing a test that reliably lands both cases ready at the same instant means synchronizing on an internal race window, which is exactly the "hunt races statistically, exercising the package in ways nobody would" pattern the skill rules out. This is inherited from the exemplar (`bucket_test.go` has the same gap over `bucket.go`), not introduced here. Flagging it here instead of adding a flaky test: the doc's ordering language should either be softened to "may return ctx.Err() if ctx is done" or the implementation should give `ctx.Done()` priority via a non-blocking pre-check, mirroring the pattern `Wait` already uses to prioritize `l.done` ahead of its main `select`. Maintainer's call which.

4. **Rejected — out of scope for this harness.** The dropped exemplar boundary case (see point 1) doesn't have its own commit with a message pointing at the finding. This iteration has no commit-per-change workflow attached to it: the output directory isn't independently git-tracked, and nothing here is being merged as a PR. The underlying concern — author-context findings belong in commit bodies, not just report prose — is right and is captured in this report instead; it'd apply once this suite lands in a real repo history.

5. **Applied** — the arithmetic in the original note was off by one: `time.Second` is `1e9` nanoseconds, so `rate == 1e9` gives a `1ns` interval, not zero. The floor only hits at `rate > 1e9`. Corrected above and in the new test's rate (`2_000_000_000`, comfortably past the threshold either way).
